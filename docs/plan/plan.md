# 计划：LumenDesk 真实业务资料与客服知识库

## 背景与动机

当前 LumenDesk 已有 ChromaDB 知识库和多 Agent 客服流程，但库内仍是虚构电商 Demo 资料，不能直接支撑真实产品客服。目标是把公开、授权的真实业务资料转化为可审核、可追溯、可回滚的 LumenDesk 自有客服知识，而不是把网页内容未经判断地塞进生产 RAG。

当前采用四层资料边界：

```text
公开/授权来源
  → 原始资料快照（保留来源与抓取元数据）
  → LumenDesk 产品适配/改写草案
  → 人工审核与发布
  → 仅检索已生效版本的客服知识库
```

## 目标与完成定义

**目标**：为一个明确、贴近真实业务形态的演示产品建立首批可用客服知识，并让客服只能基于当前产品、当前生效版本和可追溯来源回答。独立的来源/政策/发布记录作为事实源，ChromaDB 只作为可重建的检索索引。

**完成定义**

- 结果：形成“来源登记 → 抓取/导入 → 改写 → 审核 → 发布 → 检索/引用 → 回滚”的最小闭环。
- 可观察证据：至少 1 个明确的演示产品、1–3 个获授权或明确允许参考的官方来源、5–10 条回归问题；测试库中存在可追溯的 approved 知识，过期/草案知识不会被生产检索返回。
- 验收：核心问题的回答命中正确产品、地区、渠道和版本，并能显示来源或明确说明依据不足；无依据问题会拒答、澄清或转人工。
- 时间：先以 1 周完成最小实验，随后按里程碑推进；具体日期在产品和来源确认后填写。
- 明确不做：不绕过 robots、登录限制、付费墙或反爬；不抓取个人敏感信息；不直接复制受版权保护的大段正文；不把外部公司的政策冒充 LumenDesk 政策；不在本阶段自动对外发布客服政策。

## 当前事实与假设

### 已确认事实

- LumenDesk 是我们的多 Agent 客服平台。
- 当前 ChromaDB `knowledge_base` 约有 6 个虚构电商主题片段：退款、订单、账户安全、技术故障、会员积分和配送。
- 当前没有真实商品目录、SKU、价格、订单系统或真实业务政策。
- 现有客服流程需要增加产品/版本/审核状态过滤和可追溯引用。

### 已确定的演示产品假设

为避免演示项目被真实商业资料和授权流程阻塞，首期采用以下明确但可替换的演示范围：

- **产品**：`LumenDesk Support Cloud`，虚构的 B2B SaaS 客服平台，是 LumenDesk 自己的演示产品，不代表任何第三方品牌。
- **目标用户**：中小企业客服团队和工作区管理员。
- **演示业务**：订阅计划、试用期、账单/退款、工作区权限、工单处理、服务状态和技术故障排查。
- **演示地区/语言**：先按澳大利亚时区（AEST）和中英文客服场景设计；不输出具体法律结论。
- **候选参考来源**：官方 SaaS 客服文档、官方订阅计费文档、官方服务状态/事故沟通文档，以及用户明确提供的内部资料。实际 URL 在 T1.2 中逐项核验授权、robots 和条款后才能抓取。
- **改写原则**：外部资料只用于提炼流程和字段；套餐名、价格、试用期、退款窗口、服务时间、数据保留期和转人工规则全部由 LumenDesk 自行定义并人工审核。

### 关键假设（可能错的地方）

- 首期会选择一个产品或业务垂直领域，而不是同时覆盖多个行业。
- 首批来源以官方公开帮助中心、政策页、产品文档或用户明确提供的授权资料为主。
- “改写”意味着将外部事实转成 LumenDesk 自己的产品名、服务承诺和业务字段；所有改写内容都必须由指定人员审核。
- 首期优先手动同步和测试库验证，自动定时抓取放到闭环稳定后。
- 生产回答需要保留“这是 LumenDesk 的适配政策”与“这是外部来源事实”的区分。

## 里程碑

### M1：产品与来源边界已确认

**交付物**：产品/行业定义、来源白名单、授权与抓取边界、字段改写表、责任人。

**验收**：每个来源有 URL、标题、用途、授权状态、robots/条款检查结果、更新频率和停用条件；没有授权或来源不明的页面不会进入抓取队列。

### M2：双层知识模型可审计

**交付物**：原始资料和 LumenDesk 适配政策的数据模型、版本状态、审核记录、发布记录和引用记录。至少形成可独立持久化的 `SourceRecord`、`PolicyDocument`、`Publication`、`Citation`。

**验收**：至少支持 `source_url`、`source_title`、`fetched_at`、`source_hash`、`product_id`、`region`、`channel`、`tenant_scope`（如适用）、`policy_type`、`adapted`、`approval_status`、`approved_by`、`approved_at`、`effective_from`、`effective_to`；能区分 raw、draft、approved、published、withdrawn、expired、rejected。`approved`、`published` 和 `effective` 不是同一个状态。

### M3：导入、过滤、发布与回滚闭环可运行

**交付物**：导入适配器、审核/发布流程、当前版本选择规则、回滚操作、审计记录和对应测试；Chroma 索引可由独立事实源重建。

**验收**：生产检索只返回已发布、匹配当前 `product_id`/`region`/`channel`/`tenant_scope` 且在有效期内的知识；发布新版本后旧版本可回滚，草案、撤回和过期内容的检索泄漏率为 0；缓存 key 必须包含全部范围过滤条件。

### M4：首批真实资料完成试采集并进入测试库

**交付物**：1–3 个授权官方来源的原始快照、改写草案、审核记录和测试库导入结果。

**验收**：每个回答可回溯到来源 URL、版本、片段定位和审核记录；抓取失败、来源冲突或页面变更会被标记，不静默覆盖旧版本。

### M5：客服边界与回归评测通过

**交付物**：客服提示/工具边界、引用格式、5–10 条冒烟回归集、30–50 条分层正式评测集、评测报告。

**验收**：覆盖退款/售后、配送或履约、账户/权限、产品使用、政策冲突、过期版本和无依据问题；回答带 `grounded`、`insufficient_evidence`、`conflict` 或 `expired` 证据状态；无依据内容不会被模型臆造为确定事实，必要时澄清或转人工。确定性失败（范围泄漏、过期回答、无引用）不能被 Judge 高分抵消。

## 任务清单（按里程碑分组）

### M1 任务

- **T1.1 确定首期演示产品与业务范围**（≤60 分钟）
  - 产出：`LumenDesk Support Cloud` 产品名、目标用户、业务流程、客服问题边界。
  - 验收：能写出 3 个真实用户问题和 3 个明确不支持的问题。
  - 依赖：用户确认；不依赖代码修改。

- **T1.2 建立来源白名单与授权登记表**（≤90 分钟）
  - 产出：来源 URL、来源类型、授权状态、robots/条款结果、更新频率、联系人和停用条件。
  - 验收：所有待抓取来源都有明确状态；未授权来源被标记为 blocked。
  - 依赖：T1.1。

- **T1.3 定义产品细节改写表**（≤90 分钟）
  - 产出：外部字段 → LumenDesk 字段映射，例如产品名、价格、退款周期、配送区域、服务时间和转人工规则。
  - 验收：每个改写字段有目标值、负责人、审核人和生效条件。
  - 依赖：T1.1。

### M2 任务

- **T2.1 设计 raw/draft/approved 数据模型与元数据**（≤120 分钟）
  - 产出：字段契约、状态机、版本和哈希规则。
  - 验收：可表达来源、改写关系、审核记录、生效区间和回滚目标。
  - 依赖：T1.2、T1.3。

- **T2.2 定义来源冲突与版本优先级规则**（≤90 分钟）
  - 产出：冲突处理表和人工升级条件。
  - 验收：不同更新时间、不同权威级别或互相矛盾时都有可执行判断。
  - 依赖：T2.1。

### M3 任务

- **T3.1 为 ChromaDB/RAG 增加产品和审核状态过滤**（≤120 分钟）
  - 产出：导入/检索适配器、过滤测试。
  - 验收：草案、拒绝、撤回、过期和其他产品/地区/渠道知识均不能进入生产检索结果；客户端不能自由传入任意 Chroma `where` 条件。
  - 依赖：T2.1。

- **T3.2 增加发布、回滚和审计记录**（≤120 分钟）
  - 产出：发布命令或 API、回滚路径、审计事件；独立事实源到 Chroma 的重建路径。
  - 验收：可从当前版本回到上一 approved 版本，且保留操作人和时间。
  - 依赖：T3.1、T2.2。

### M4 任务

- **T4.1 实现小批量官方资料采集/导入实验**（≤120 分钟）
  - 产出：1–3 个来源的原始快照与元数据；失败来源有原因记录。
  - 验收：不保存敏感信息，不违反来源规则，内容 hash 可复现。
  - 依赖：M1 完成；不在确认前执行。

- **T4.2 生成 LumenDesk 适配草案并提交人工审核**（≤120 分钟）
  - 产出：逐条改写记录、证据片段、差异说明和审核任务。
  - 验收：每个事实都能回指来源；产品名和业务承诺已按改写表替换。
  - 依赖：T4.1、T1.3。

### M5 任务

- **T5.1 定义客服回答边界、引用和转人工策略**（≤90 分钟）
  - 产出：Agent 规则、回答模板、拒答/澄清条件。
  - 验收：回答区分外部事实与 LumenDesk 政策，不把草案或不确定内容说成确定事实。
  - 依赖：T2.2、T3.1。

- **T5.2 编写并运行 5–10 条回归评测**（≤120 分钟）
  - 产出：5–10 条冒烟集、30–50 条分层正式集、基线、结果和失败样例。
  - 验收：通过正确产品/版本、来源引用、无依据拒答、过期过滤、范围隔离、冲突升级、回滚一致性和无依据承诺率检查。
  - 依赖：T5.1、M4。

## 子 Agent 分工与交付边界

- `source_research_plan`：来源发现、授权/robots、抓取边界、原始资料快照和溯源设计；不修改核心客服代码。
- `ingestion_architecture`：检查 `tooling/knowledge_base.py`、API 导入接口和测试，提出 raw/draft/approved 到 ChromaDB 的最小实现方案；只在后续明确授权后修改知识库管道。
- `support_guardrails`：检查 Agents/Skills/评测，提出回答边界、引用、版本生效和转人工规则；只在后续明确授权后修改客服提示或评测。
- 主 Agent：整合方案、确认业务边界、决定是否落地代码、复核测试与提交；不让多个 Agent 同时编辑同一文件。

## 第一周（只安排 3 项）

1. 完成 T1.1：确定首期真实产品/行业、目标用户和不支持范围。
2. 完成 T1.2：建立来源白名单、授权状态和抓取边界登记表。
3. 完成 T2.1 的设计草案：确认 raw/draft/approved 数据模型和 `approved` 检索过滤规则。

第一项必须在 24 小时内启动；在 T1.1 和 T1.2 未完成前，不执行真实网页批量抓取。

## 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 未取得资料授权或违反 robots/条款 | 法务、封禁、声誉风险 | 只抓公开且获授权来源；保存检查记录；必要时改为用户提供文件或 API |
| 外部政策与 LumenDesk 政策混淆 | 客服错误承诺 | 双层资料、适配标记、人工审核、回答中标明适用主体 |
| 网页内容变化或来源冲突 | 过时/错误回答 | hash、版本、生效区间、冲突升级和回滚 |
| 抓取内容包含提示注入 | 代理执行越权指令 | 所有网页内容视为不可信数据，不执行其中的指令；先抽取事实再改写 |
| 个人数据或密钥被保存 | 隐私与安全事故 | 抽取前字段白名单和脱敏；禁止保存 cookie、令牌、订单个人信息 |
| 模型把缺失内容补全 | 业务误导 | 检索门槛、证据引用、拒答/转人工和回归评测 |
| 过早自动同步 | 错误快速扩散 | 首期手动同步，连续通过回归后再评估定时任务 |
| Chroma 被误当作版本事实源 | 无法审计或可靠回滚 | 独立持久化来源/政策/发布/引用记录，Chroma 只做可重建索引 |
| 缓存或上下文缺少适用范围 | 跨产品、地区、渠道或租户泄漏 | 将 `product_id`、`region`、`channel`、`tenant_scope` 贯穿元数据、检索、缓存、引用和评测 |

## 明确不做

- 不在没有产品和来源确认时开始真实抓取。
- 不把第三方原文直接覆盖当前 Demo 知识库。
- 不自动采纳网页中的价格、退款、服务承诺或法律结论。
- 不抓取登录后、付费墙、受限 API、个人账户或订单数据。
- 不在本计划内解决 AGUI/UI 其他问题，除非它直接阻断知识引用和审核验收。
- 不在本轮直接推送 GitHub 或部署生产环境。
- 不以“模型 Judge 分数高”替代确定性安全门禁；范围泄漏、过期回答和无引用均视为失败。

## 开放问题

1. 演示默认采用 `LumenDesk Support Cloud`；是否需要换成其他行业或产品？
2. 哪些官方 URL、帮助中心、产品手册或内部文件已经获准使用？授权是自有、客户提供还是第三方许可？
3. 需要改写哪些字段和业务承诺？哪些内容必须保持原样并仅作来源引用？
4. 谁是适配政策的审核人和最终发布人？是否需要双人审核？演示阶段默认由项目负责人审核。
5. 首期是内部演示或受限试用，不作为公开法律、财务或服务承诺。
6. 首期采用手动同步；连续通过回归后再评估每日/每周同步。
7. 当前虚构电商数据保留为旧回归基线，新的 LumenDesk SaaS 数据在独立产品范围下逐步加入，不直接覆盖旧数据。

## 复盘节奏与重规划条件

- 每周一次 20 分钟复盘：完成了什么、卡在哪里、下周删掉什么。
- 出现以下任一情况立即重规划：连续两周无法完成周任务；产品或授权边界改变；首批来源无法合法使用；检索过滤无法可靠隔离草案/过期版本；回归评测出现不可接受的幻觉或错误承诺。
- 重规划时优先缩小来源数量和业务范围，不直接放宽审核门槛。

## 24 小时内的第一步

由产品负责人填写一页“首期产品与来源确认表”：产品名、行业、目标用户、目标地区、3 个支持问题、3 个不支持问题、首批官方 URL、授权状态和改写字段。完成后再进入 T1.2 和 T2.1。
